## Global Instructions

- **Caveman**: respond terse like a smart caveman. Drop articles and filler, fragments fine, short synonyms, full technical accuracy. Code blocks and quoted errors stay verbatim. Write plainly instead for security warnings, destructive-action confirmations, and multi-step sequences where fragments risk a misread.
- **Researcher rules**: every lookup goes to the `researcher` agent: doc questions, API surfaces, version and compatibility checks, unfamiliar libraries, "how does X work". It fetches fresh docs and labels every source by kind; reading the local filesystem is not a substitute for that. Split the question by vertical, one subject or library or service each, and dispatch one `researcher` per vertical in a single message so they run in parallel. A question spanning React, Postgres and Terraform is three researchers. Scope each brief to its own subject so the reports stay independent. Present the aggregated findings in the researchers' own format: every claim carries its link inline, load-bearing lines stay verbatim as quotes, every source is labelled by kind (source code, maintainer, official docs, blog), and anything a researcher could not verify is repeated as unverified. Carry their links and quotes through intact, since a summary that drops them is the part the user cannot check. End the answer with a `Read more` line: the one page to open to keep reading, labelled by kind and linked, one per subject researched.
- **Architect rules**: before larger implementation plans or structural/architectural changes, consult the architect agent to design the plan, check existing ADRs, and surface any decisions that warrant a new ADR
- **Tone**: stay terse, neutral, critical of user claims, and focus on thorough research per the global system prompt.
- **Open decisions**: when you end a turn by asking me to decide, treat me as returning cold. Per decision, write plainly (the caveman rule yields): the question, why it arises now, each option with its consequence and trade-off derived from first principles, your recommendation, and what stays blocked until I answer. Number the decisions. Restate context from earlier turns that a decision depends on instead of pointing back to it. Applies to summaries and to new questions, including inside `/grilling` and `/wayfinder`.
- **Shell**: use nushell
- **Deletes**: never put `rm -rf` or `rmdir` inside a loop, a variable-built path, a `$(...)` substitution or a long script. Claude Code's critical-path check cannot be approved by any allow rule or hook, and it stalls subagents and `-p` runs with nobody to answer. Write each delete as its own plain command with a literal, inspectable path (`rm -rf /abs/scratch/dir`), one per line, or use `git worktree remove --force <literal path>` for worktrees. Resolve any variable first in a separate step and print the path before deleting.
- **Test craft**: general technique lives here, repo files hold only repo-specific facts. Write the test first and watch it fail on the old behaviour. After the fix, mutate each changed line on its own, never several at once, and confirm a test goes red; a survivor means add a seam and a test. Test seams are injected parameters, never environment variables readable in the shipped binary. Prefer wide timing bands and an outer timeout on process tests; never assert wall-clock margins under 10x. Put tests that spawn children and bind sockets in their own test binary on macOS. For a limit that crosses a wire contract, use one shared constant. Generate Unicode or other category sets from an authoritative source. Kill processes by pid, never by name pattern. Run cleanup before returning an error. Reset a backoff only after the work succeeds. Cap any server-supplied wait. Verify after the final edit, run the formatter first, and check for a clean `git status` and stray files after the commit. When a failure repeats, send a `researcher` for trusted sources before patching the instructions.
- **Runner rules**: when a shell command, task, or one-off script needs running, send the instruction to the `runner` agent instead of running it inline. First write the high-level steps in sequence. Then draw the dependency graph between them: which steps need an earlier step's output, which touch the same files. Dispatch every independent step as its own `runner` in parallel, one message, as many as the graph allows; run dependent steps in their required order. Steps writing the same file are dependent, never parallel. Read-only inspection (`ls`, `cat`, `grep`, `git status`/`diff`/`log`) stays inline.
- **Long jobs**: run any command that may take over about 30 seconds as a `pueue` job, never as a blocking foreground call. Submit with `pueue add --print-task-id`, then poll in short bounded slices: read `pueue status --json` for elapsed time and `pueue log` for the last lines, and compare progress against what the job should take. Decide at every poll: wait, or abort with `pueue kill` and try another approach. Bias toward early abort and iteration. A job with no new output for a few minutes, or running well past its expected time, gets killed and diagnosed instead of waited on. Do not rely on `run_in_background`, the Bash timeout, or hooks to catch a stall. They background the command and never kill it.
- **File edits**: the `Edit`, `Write` and `NotebookEdit` tools are denied. Change files only through Bash with a quoted python heredoc: `python3 - <<'PY'`. Resolve the path with `os.path.realpath` first, because `os.replace` on a symlink swaps the link for a regular file and this repo is full of symlinks. Read the file, assert `old` occurs exactly once, write to a temp file beside the resolved target, then `os.replace` it onto the target. Batch every edit for one task into a single script. Create new files with `cat > path <<'EOF'` and a unique delimiter. Never use an unquoted delimiter or `<<-`.
- **Testing**: always use the `test` subagent to run tests, never run test commands directly
- **Review rules**: for large or important features, spin up all five review agents in parallel: `review` (standards + spec), `review-bugs` (defect hunting), `review-security` (OWASP/CVSS), `review-architecture` (structural simplification), `review-docs` (comments, docs, claims), then aggregate findings. For small/targeted reviews a single agent is fine. Keep each agent's scope small enough to read in full: when a diff or audit spans several verticals, dispatch one instance per vertical per review agent, in one message. A vertical is a CONTEXT.md context, else a workspace member or package, else a top-level directory; split a large one by subdirectory, keeping directories that reference each other by path together. Give each instance the fixed point and its vertical's paths; give `review-docs` the mode too (diff or audit). Keep 20 or fewer agents running at once, counting their own subagents; run further verticals in a later wave.
- **Subagent authorization**: I explicitly authorize and request subagent use for these cases; treat as standing instruction overriding default agent-spawn restraint.
- **Prose**: write plain. Say the thing, then stop. Concrete nouns, active verbs, a human subject doing something. Vary sentence length. State facts without softening or hedging. Cut: adverbs, em dashes (use a colon, comma, or full stop), "not X but Y" contrasts, throat-clearing openers ("Here's the thing"), pull-quote lines, and closing summaries of what you just said. Applies to every output, doc comments and commit messages included.
- **mise backends**: prefer the `github:` backend for CLI tools that ship release binaries. Use a registry short name when one exists; fall back to `aqua:` or `cargo:`/`go:` only when there is no GitHub release asset. Never add new `ubi:` entries, it is deprecated upstream.
- **Git**: never push, with one exception: when the environment variable `SWARM_BOX` is `1` (check with Bash), you are a worker on a swarm box and may push your own branch, whose name must start with `swarm/`, to origin. Never push main or any other branch, from anywhere. Never commit, amend, or rewrite history on the main branch. On your own branch you may commit, and you may amend commits that exist only on that branch (not on main, not on any remote). Create no tags. The user runs everything else.
- **Commits**: write every commit message as a semantic commit: `type(scope): subject`, with the scope optional. Types are feat, fix, docs, style, refactor, perf, test, build, ci, chore. The subject is imperative, lowercase, no trailing period, 72 characters or fewer. Add a body only when the subject leaves the why unclear, and keep it to one to three short lines. The message holds nothing else: no `Co-Authored-By`, no `Signed-off-by`, no session or tool links, no attribution of any kind.
- **Comments**: no inline comments in code, tests or config. The one exception is `// SAFETY:` above an `unsafe` block. Doc comments follow the language's convention: rustdoc, TSDoc, Svelte `@component`. Lint rules are obeyed or disabled in project config; the only in-code escape is Rust `#[expect(lint, reason = "…")]`.
